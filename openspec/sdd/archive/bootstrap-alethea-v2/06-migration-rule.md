## Rule (proposed for a future `legacy-cleanup` change)

A migration is a candidate for archival if and only if **all** of the following hold:

1. The migration is older than the current calendar month AND has not been edited in the last 90 days.
2. The schema it creates/alters has zero rows in any environment (dev, staging, prod) for at least 30 consecutive days.
3. The migration is not referenced by name in any application code (search `priv/repo/migrations/*.exs` and `lib/`, `test/`).
4. The corresponding schema is fully covered by a newer migration (e.g., column added here, renamed/dropped by a later migration).
5. The deletion is reviewed by at least one other engineer and the PR description documents what data, if any, is at risk.

The archival process:
- Move the file under `priv/repo/migrations/archive/YYYY-MM-DD-{name}.exs` with a banner comment at the top: `# ARCHIVED on {date} — see {archive reason} — see {follow-up migration}`. The file is renamed, not deleted (the original Ecto timestamp ordering is preserved in the archive folder name).
- Do **not** alter the file contents inside the archive.
- Add a CHANGELOG entry in `openspec/sdd/{change}/archive-notes.md`.

## Why we are NOT deleting anything in this change

- No production database is in use, but deleting a migration is irreversible once a fresh DB is created from this repo.
- The 224-test baseline depends on the migration ordering; deleting a file out of order can break `ecto.migrate` on a fresh checkout.
- The user did not ask for destructive migration cleanup in this change.
- A future change that owns deletion can do it deliberately, with the rule above as a guard.

## What this change does to migrations

Nothing. This change ships no new migrations. The `Alethea.Foundation.*` schemas are added as **schemas-without-tables**: they compile and test against the existing `Repo` setup but are not migrated. The first migration that creates `foundation_professionals`, `foundation_patients`, `foundation_admins` will be generated by the change that actually uses them (e.g., `psicologo-foundation`).

If the next change does want a foundation migration, the timestamp prefix should be `2099...` or similar (clearly out of normal sequence) to keep the visual signal that "foundation is a parallel track."

## Open question for future changes

- Should the foundation tables be `foundation_professionals` (parallel, no collision) or just `professionals` (shadowing legacy, with a follow-up rename)? **Default recommendation: `foundation_professionals` until a dedicated rename change is approved.** The legacy `professionals` table is in active use.
